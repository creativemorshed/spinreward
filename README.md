# SpinReward (Next.js + TypeScript + Tailwind + Supabase)

রেস্টুরেন্টের টেবিলে QR → কাস্টমার স্পিন করে ক্যাশ ডিসকাউন্ট জেতে → ক্যাশিয়ার কুপন রিডিম করে → মালিক ড্যাশবোর্ডে সব দেখে।

## ফিচার (Step 1–3)

| Step | কী আছে | কোথায় |
|------|--------|--------|
| 1 | ৮-segment SVG চাকা, ৫.২ সেকেন্ডের ease-out অ্যানিমেশন, সার্ভার-সাইড weighted random, কুপন কোড | `src/components/SpinWheel.tsx`, `src/app/api/spin/route.ts` |
| 2 | প্রতি রেস্টুরেন্টের ইউনিক QR (`/r/<slug>`), PNG ডাউনলোড | `src/app/api/qr/[slug]/route.ts` |
| 3 | মোট স্পিন / কুপন / রিডিম, সবচেয়ে বেশি জেতা পুরস্কার, দৈনিক চার্ট, QR কার্ড, কুপন রিডিম | `src/app/dashboard/page.tsx`, `src/app/api/dashboard`, `src/app/api/redeem` |

## Viral Loop (Step 4)

```
স্পিন → জেতা/হারা → শেয়ার (+১ বোনাস স্পিন, দিনে ১ বার)
      → বন্ধু /r/<slug>?ref=<কোড> লিংকে ঢোকে → প্রথম স্পিন করে
      → শেয়ারকারী +১ বোনাস স্পিন (দিনে সর্বোচ্চ ৩ জন) → আবার শেয়ার …
```

| নিয়ম | মান |
|-------|-----|
| ফ্রি স্পিন | প্রতি ভিজিটর, প্রতিদিন ১টি (ঢাকার সময়) |
| শেয়ার বোনাস | +১, দিনে একবার |
| রেফারেল বোনাস | বন্ধুর **প্রথম স্পিনের** পর +১; একজন রেফারার দিনে সর্বোচ্চ ৩ জনের জন্য |
| বোনাস জমার সীমা | ৫ |
| ড্যাশবোর্ড | মোট ভিজিটর, শেয়ার থেকে আসা নতুন ভিজিটর, বোনাস স্পিন ব্যবহার |

**আপগ্রেড করার সময়:** আগে `schema.sql` চালিয়ে থাকলে এখন শুধু `supabase/002_viral_loop.sql` Run করুন (বারবার চালালেও সমস্যা নেই)। নতুন সেটআপে দুটোই ক্রমান্বয়ে চালান।

**অপব্যবহার ঠেকানো:**
- রেফারেল লিংকে `visitor_id` নয়, আলাদা `ref_code` থাকে।
- নিজের লিংকে নিজে ঢুকলে এবং আগে স্পিন করা ভিজিটরের রেফারেল গণ্য হয় না।
- বোনাস শুধু বন্ধুর স্পিন করার পরে মেলে, লিংকে ক্লিক করলেই নয়।
- সব ব্যালেন্স পরিবর্তন DB ফাংশনে atomic; একসাথে অনেক রিকোয়েস্টেও বোনাস ঋণাত্মক হয় না।

**সত্যিটা জানা দরকার:** Facebook আসলেই পোস্ট হয়েছে কি না সার্ভার যাচাই করতে পারে না। তাই শেয়ার বোনাস "শেয়ার বাটনে চাপ" ধরে দেওয়া হয় (দিনে ১টি সীমায়)। রেফারেল বোনাসে এই সমস্যা নেই, কারণ সেটা আসল নতুন ভিজিটরের স্পিনের উপর নির্ভর করে।

## Admin Panel (Step 5)

`/admin` — শুধু `platform_admins` টেবিলের ইউজাররা ঢুকতে পারেন (বাকিরা 403)।

| ট্যাব | কী করা যায় |
|-------|-------------|
| **ওভারভিউ** | MRR, এই মাসের/মোট আয়, ট্রায়াল/শীঘ্রই-শেষ/মেয়াদ-শেষ/স্থগিত সংখ্যা, প্ল্যাটফর্মের স্পিন-কুপন-ভিজিটর, দৈনিক চার্ট, ৬ মাসের আয়, শীর্ষ ৫ রেস্টুরেন্ট |
| **রেস্টুরেন্ট** | নতুন রেস্টুরেন্ট + মালিকের অ্যাকাউন্ট তৈরি (অস্থায়ী পাসওয়ার্ড একবার দেখায়), খোঁজা/ফিল্টার, প্ল্যান বদল, স্থগিত/চালু |
| **পেমেন্ট** | bKash/Nagad/Rocket/ব্যাংক/ক্যাশের পেমেন্ট রেকর্ড (মেয়াদ অটো বাড়ে), TrxID-র ডুপ্লিকেট ঠেকানো, রেস্টুরেন্টভিত্তিক খাতা |

**সাবস্ক্রিপশন নিয়ম**
- নতুন রেস্টুরেন্ট = ১৪ দিন ফ্রি ট্রায়াল (`service_until`)।
- পেমেন্ট রেকর্ড করলে নতুন মেয়াদ = max(পুরনো মেয়াদ, আজ) + দিন সংখ্যা; প্ল্যানও পেমেন্টের প্ল্যানে বদলায়।
- মেয়াদ শেষ বা স্থগিত হলে কাস্টমারের `/r/<slug>` "সাময়িক বন্ধ" দেখায় এবং spin/visitor/share API বন্ধ হয়। মালিক ড্যাশবোর্ডে ঢুকতে পারেন (মেয়াদ শেষ হলে ব্যানার দেখেন); স্থগিত হলে ঢুকতে পারেন না।
- পেমেন্টের ইতিহাস থাকা রেস্টুরেন্ট মোছা যায় না — স্থগিত করুন।
- দাম বদলাতে `src/lib/plans.ts`-এর `PLAN_PRICE` এডিট করুন (MRR ও ফর্মের ডিফল্ট দুটোই এখান থেকে)।

**প্রথম অ্যাডমিন বানানো** (`003_admin_panel.sql` Run করার পর, একবার):
1. Supabase → Authentication → Users → Add user
2. SQL Editor:
   ```sql
   insert into public.platform_admins (user_id)
   select id from auth.users where email = 'you@example.com';
   ```
3. `/login?next=/admin` দিয়ে লগইন করুন।

⚠️ **আপগ্রেডের ক্রম:** আগে Supabase-এ `003_admin_panel.sql` Run করুন, *তারপর* নতুন কোড ডিপ্লয় করুন। উল্টো করলে স্পিন-পেজ `service_until` কলাম না পেয়ে বন্ধ হয়ে যাবে। মাইগ্রেশনের পর আগের সব রেস্টুরেন্ট আজ থেকে ১৪ দিনের ট্রায়াল পাবে।

## পেমেন্ট নবায়ন, রিমাইন্ডার ও অ্যান্টি-ফ্রড (Step 6)

> ⚠️ **ডিপ্লয়ের ক্রম:** আগে Supabase-এ `supabase/004_payments_reminders_antifraud.sql` Run করুন, *তারপর* নতুন কোড ডিপ্লয় করুন।
> উল্টো করলে স্পিন-পেজ নতুন কলাম (`ip_hash`, `last_ip_hash`) না পেয়ে ব্যর্থ হবে।

### ১) মালিকের নবায়ন অনুরোধ + অ্যাডমিন অনুমোদন
- মালিকের ড্যাশবোর্ডে **"সাবস্ক্রিপশন নবায়ন"** কার্ড: প্ল্যান ও মাস (১/২/৩/৬/১২) বেছে নিলে পাঠানোর পরিমাণ দেখায়, bKash/Nagad/Rocket/ব্যাংকের নম্বর দেখায় (আপনার env থেকে), মালিক টাকা পাঠিয়ে **TrxID** জমা দেন।
- পরিমাণ ও মেয়াদ **সার্ভারে গণনা হয়** (প্ল্যানের দাম × মাস) — ক্লায়েন্টের পাঠানো সংখ্যা বিশ্বাস করা হয় না।
- অ্যাডমিন প্যানেলের নতুন **"অনুরোধ"** ট্যাবে (অপেক্ষমাণ সংখ্যা ব্যাজে দেখায়) এক ক্লিকে **অনুমোদন** বা কারণসহ **বাতিল**। অনুমোদনে পেমেন্ট খাতায় ওঠে, মেয়াদ বাড়ে ও প্ল্যান বদলায় — সবটা একটি ট্রানজেকশনে।
- সুরক্ষা: একই TrxID দুইবার জমা/রেকর্ড হয় না (বাতিলের পর আবার জমা দেওয়া যায়); একসাথে সর্বোচ্চ ৩টি অপেক্ষমাণ অনুরোধ; খাতায় আগেই থাকা TrxID-র অনুরোধ অনুমোদন ব্যর্থ হয় ও pending-ই থাকে।
- **এটি স্বয়ংক্রিয় গেটওয়ে নয়।** টাকা সত্যিই এসেছে কি না সিস্টেম যাচাই করতে পারে না — অনুমোদনের আগে নিজের bKash/Nagad অ্যাপে TrxID ও পরিমাণ মিলিয়ে নিন। আসল গেটওয়ে (bKash Tokenized Checkout ইত্যাদি) মার্চেন্ট অ্যাকাউন্ট ও ক্রেডেনশিয়াল চায়; পেলে `review_payment_request`-এর আগে ওই যাচাই বসানো যাবে।

### ২) মেয়াদ-রিমাইন্ডার ইমেইল
- প্রতিদিন সকাল ১০টায় (ঢাকা) Vercel Cron `/api/cron/reminders` চালায় (`vercel.json`)।
- মেয়াদ শেষের **৭, ৩, ১ দিন আগে** এবং **শেষ হওয়ার পর (৩ দিন পর্যন্ত)** মালিককে ইমেইল যায়। স্থগিত ও মালিকহীন রেস্টুরেন্ট বাদ।
- একই ইমেইল কখনও দুইবার যায় না (পাঠানোর আগে "দখল"; ব্যর্থ হলে দখল ছেড়ে দেয়, পরের দিন আবার চেষ্টা)। নবায়নে মেয়াদ বদলালে নতুন চক্র শুরু হয়।
- সেটআপ: [Resend](https://resend.com)-এ অ্যাকাউন্ট খুলে ডোমেইন ভেরিফাই করুন → Vercel env-এ `RESEND_API_KEY`, `EMAIL_FROM`, `CRON_SECRET` দিন। `CRON_SECRET` না থাকলে এন্ডপয়েন্ট বন্ধ (503) থাকে; ইমেইল কনফিগ না থাকলে কিছু পাঠায় না ও কিছু "দখল"ও করে না।
- পরীক্ষা: `curl -H "Authorization: Bearer $CRON_SECRET" "https://your-app/api/cron/reminders?dry=1"` — কাকে কী পাঠানো হতো তা দেখায়, কিছু পাঠায় না।
- Vercel Hobby প্ল্যানে দিনে একবারের বেশি cron চলে না — এখানে ঠিক একবারই লাগে।
- SMS নেই (বাংলাদেশি SMS প্রোভাইডারের আলাদা ক্রেডেনশিয়াল লাগে)।

### ৩) IP-ভিত্তিক অ্যান্টি-ফ্রড
| সুরক্ষা | নিয়ম |
|---------|-------|
| **Burst সীমা** | এক IP থেকে মিনিটে সর্বোচ্চ ৬০ অনুরোধ (visitor/spin/share/নবায়ন মিলিয়ে) — স্ক্রিপ্ট ঠেকাতে |
| **দৈনিক IP সীমা** | এক IP থেকে এক রেস্টুরেন্টে দিনে সর্বোচ্চ ১০০ স্পিন |
| **রেফারেল-ফার্মিং** | রেফারেল দেওয়া ও পাওয়া ডিভাইস একই IP-তে (প্রথম/সর্বশেষ/বর্তমান যেকোনোটিতে মিললে) হলে বোনাস নেই; ব্লক হওয়া রেফারেল দৈনিক সীমা (৩) খরচ করে না |

- **গোপনীয়তা:** আসল IP কখনও ডাটাবেসে যায় না — শুধু সল্টযুক্ত SHA-256 হ্যাশ। IPv6 হলে প্রথম ৬৪ বিট (/64) ধরা হয়, কারণ মোবাইল ক্যারিয়ার একই ডিভাইসকে ঘনঘন নতুন ঠিকানা দেয়।
- **সীমা ইচ্ছাকৃতভাবে উদার।** রেস্টুরেন্টের WiFi-তে সব কাস্টমার একই IP-তে থাকে। ব্যস্ত রেস্টুরেন্টে সমস্যা হলে `MAX_SPINS_PER_IP_PER_DAY` / `MAX_REQUESTS_PER_IP_PER_MINUTE` env বাড়ান।
- **ফেল-ওপেন:** ডাটাবেস ত্রুটি বা IP অজানা হলে অনুরোধ আটকানো হয় না — বৈধ কাস্টমার যেন ভুগতে না হয়।
- Vercel `x-vercel-forwarded-for` হেডার নিজে বসায় (নকল করা যায় না)। অন্য সার্ভারে চালালে প্রক্সিতে `x-forwarded-for` overwrite করুন, নইলে ক্লায়েন্ট IP নকল করতে পারবে।
- `IP_HASH_SALT` সেট করুন; পরে বদলালে শুধু চলমান দিনের IP-সীমা রিসেট হয়।

3. Authentication → Users → **Add user** (রেস্টুরেন্ট মালিকের ইমেইল/পাসওয়ার্ড), তার UUID কপি করুন
4. SQL Editor-এ রেস্টুরেন্ট বানান (৮টি ডিফল্ট পুরস্কার অটো তৈরি হবে):
   ```sql
   insert into public.restaurants (owner_id, name, slug, plan)
   values ('<ইউজার-uuid>', 'Sampan Restaurant', 'sampan', 'standard');
   ```
5. `.env.local` বানান (`.env.example` দেখুন) এবং চালান:
   ```bash
   npm install
   npm run dev        # http://localhost:3000
   npm test           # লজিক + SQL টেস্ট (আসল Postgres WASM-এ)
   npm run build && npm run test:api   # API টেস্ট (mock Supabase ও Resend দিয়ে)
   ```
6. `/login` → লগইন → ড্যাশবোর্ড। `/r/sampan` কাস্টমারের পেজ।

## Vercel-এ ডিপ্লয়

1. GitHub-এ push করুন (`.env*` নয়)
2. Vercel → Import → Environment Variables-এ চারটি ভ্যারিয়েবল দিন (`.env.example`)
3. `SUPABASE_SERVICE_ROLE_KEY` কখনও `NEXT_PUBLIC_` দিয়ে শুরু করবেন না
4. Deploy-এর পর `NEXT_PUBLIC_SITE_URL` আসল ডোমেইনে সেট করুন, তারপর QR আবার ডাউনলোড করুন

## নিরাপত্তার সিদ্ধান্ত

- সব টেবিলে RLS চালু, কোনো public policy নেই; ডেটা শুধু সার্ভার API দিয়ে যায়।
- Reward বাছাই সার্ভারে `crypto.randomInt` দিয়ে; ক্লায়েন্ট শুধু ফলাফল অ্যানিমেট করে। weight কাস্টমারকে পাঠানো হয় না।
- "দিনে ১ স্পিন" DB unique constraint (`restaurant + visitor + দিন`) দিয়ে — একসাথে অনেক রিকোয়েস্ট পাঠিয়েও পার পাওয়া যায় না।
- কুপন রিডিমে `status = 'active'` শর্ত থাকায় একই কুপন দুইবার রিডিম হয় না।

## জানা সীমাবদ্ধতা

- **সম্পূর্ণ ফ্লো আসল Supabase/Vercel/Resend-এ এখনও চালানো হয়নি।** SQL আসল Postgres-এ (pglite) এবং API mock Supabase/Resend-এ টেস্ট হয়েছে; ব্রাউজারে UI ও আসল ইমেইল পাঠানো প্রথমবার আপনার সেটআপেই দেখা হবে।
- `visitor_id` ব্রাউজারের localStorage-এ থাকে; ডেটা মুছলে আবার ফ্রি স্পিন সম্ভব। IP সীমা (উদার) শুধু বড় আকারের অপব্যবহার ঠেকায়। ভিন্ন IP (মোবাইল ডেটা/VPN) ব্যবহার করে নিজের রেফারেল ফার্ম করা এখনও সম্ভব — দৈনিক সীমা ৩ ক্ষতি সীমিত রাখে।
- Facebook আসলে পোস্ট হয়েছে কি না যাচাই করা যায় না; শেয়ার-বোনাস বাটনে চাপ দিলেই মেলে (দিনে ১টি)।
- পেমেন্ট স্বয়ংক্রিয়ভাবে যাচাই হয় না; অ্যাডমিনকে হাতে মিলিয়ে অনুমোদন করতে হয় (ওপরে দেখুন)।
- রিমাইন্ডার শুধু ইমেইলে; SMS নেই। ইমেইল ডেলিভারি Resend ও ডোমেইন ভেরিফিকেশনের উপর নির্ভরশীল।
- "পাসওয়ার্ড ভুলে গেছি" পেজ নেই; অ্যাডমিন Supabase থেকে রিসেট করতে পারেন। (পাসওয়ার্ড *পরিবর্তন* ড্যাশবোর্ডে আছে।)
- প্ল্যানভেদে ফিচার সীমা (যেমন পুরস্কার কাস্টমাইজ শুধু Standard+) কার্যকর নয়; প্ল্যান এখন দাম ও MRR-এর জন্য। রেস্টুরেন্টের পুরস্কার বদলানোর UI-ও নেই (ডিফল্ট ৮টি; বদলাতে SQL)।
